# ADR-0007: Generated Xcode project

- **Status:** Accepted
- **Date:** 2026-08-15
- **Deciders:** iOS maintainers

## Context

`project.pbxproj` is Xcode's project file. It is a machine-written plist with a UUID for
every file reference, build phase, and target membership, and Xcode rewrites large parts
of it in response to actions that changed nothing meaningful — opening a target editor,
reordering a group, adding a file.

Committed, it produces two problems that get worse as a team grows:

1. **Every branch conflicts with every other branch.** Two people adding one file each
   collide in a section of UUID-keyed entries that no merge tool can resolve
   semantically, and no human can review. The standard resolution is to take one side and
   re-add the other's files by hand.
2. **It is unreviewable.** A diff of four hundred pbxproj lines might be a new file, or a
   changed signing identity, or a build setting silently overridden for one configuration.
   A reviewer cannot tell, so it gets approved unread — which is where an accidental
   `CODE_SIGN_STYLE` change lives until it breaks a release build.

This project also has four targets — app, widget extension, unit tests, UI tests — with
shared settings between them, which is precisely the structure pbxproj expresses worst.

## Decision

`Plink.xcodeproj` is generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen) from
`ios/project.yml`, and is not tracked. `*.xcodeproj/` is in `.gitignore`.

- Structure changes — targets, settings, dependencies, resource phases, Info.plist
  properties — are edits to `project.yml`, which is YAML and reviewable.
- Source files are picked up by directory glob (`sources: - path: Plink`), so adding,
  moving, or renaming a file requires no project edit at all. This is the largest single
  benefit: directory reorganisation becomes free.
- `xcodegen generate`, or `make xcode` from the repository root, produces the project. It
  is required after any `project.yml` change and after adding files outside Xcode.
- A pull request containing `project.pbxproj` is rejected.

## Consequences

### What this makes easier

- Merge conflicts in project structure are conflicts in YAML, on the lines that actually
  changed, and a reviewer can read them.
- Build settings are visible and commented. `project.yml` explains _why_ a setting is
  what it is — for instance, why the associated-domains entitlement is absent
  ([ADR-0008](0008-legacy-bundle-identifier.md) covers the related identifier
  constraint).
- Moving directories costs nothing, which matters for a codebase that has reorganised
  its feature folders more than once.
- Shared settings are declared once instead of copied across four targets, so they cannot
  drift between them.

### What this makes harder

- **XcodeGen is a required tool.** A contributor without it cannot open the project, and
  the failure — no `.xcodeproj` in the directory — is confusing until someone explains
  it. This belongs in onboarding, and does.
- Changes Xcode makes through its own UI are discarded on the next generate. Adding a
  capability in the Signing & Capabilities tab appears to work and then vanishes, which
  is a genuinely surprising failure.
- A new Xcode release can change what a correct project file looks like, and the fix
  waits on an XcodeGen release. This is a real dependency on a third-party tool for the
  ability to build at all.
- Glob-based sources mean a stray file in the tree becomes part of the target. Excludes
  are needed for anything that should not compile — and one of them is load-bearing here:
  a stale `Localizable.strings` under `Localization/` collides with the real `.lproj`
  resources and breaks the build with "Multiple commands produce…" if it is not excluded.

### What has to be true for this to keep working

- XcodeGen stays maintained and keeps up with Xcode. If it stalls a major version behind,
  the cost of this decision inverts.
- Nobody needs a project-level feature XcodeGen cannot express. So far the only gap has
  been capabilities that a Personal Team cannot provision anyway.

## Alternatives considered

**Commit the pbxproj.** The default, and it requires no tooling. Rejected on the merge
and review costs above, which are paid on every pull request rather than once.

**Swift Package Manager as the build system.** Attractive — no project file, all
declarative. Rejected because an iOS app with a widget extension, entitlements, asset
catalogs, and multiple Info.plists is not something SPM builds on its own. It works for
libraries; this is an app.

**Tuist.** More capable than XcodeGen: Swift-defined projects, caching, better handling of
large modular codebases. Rejected as heavier than needed for four targets, and its Swift
manifests are a bigger conceptual step than a YAML file for contributors who mostly do
not touch project structure at all.
