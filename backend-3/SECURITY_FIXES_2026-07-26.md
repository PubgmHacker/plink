# Plink backend — исправления безопасности 26.07.2026

Все правки проверены компилятором TypeScript (изолированно, с shim-декларациями для внешних модулей). **Живой прогон на Postgres/Redis не выполнялся** — обязательно прогнать тесты и деплой на staging перед продом.

---

## P0-1 — Проверку покупок можно было подделать (критично)

**Где:** `src/utils/jose-config.ts` (живой путь через `src/routes/billing.ts`).

**Суть.** Подпись JWS от StoreKit проверялась против сертификата, взятого **из самого JWS** (`x5c[0]`), то есть против ключа, который прислал клиент. Корневые сертификаты Apple загружались, но использовались лишь как флаг «есть/нет» — цепочка `leaf ← intermediate ← root` **никогда не валидировалась**. Плюс был указан алгоритм `RS256`, тогда как Apple подписывает `ES256`.

Итог: доверие было вывернуто наизнанку. Любой человек с curl генерировал самоподписанный сертификат, подписывал им произвольный payload и получал **Premium навсегда**, а настоящие покупки Apple при этом **отвергались**.

**Исправлено:**
- обязателен `alg === 'ES256'` и цепочка `x5c` минимум из двух звеньев;
- каждое звено проверяется подписью следующего;
- корень сверяется с закреплённым Apple Root CA по отпечатку SHA-256;
- проверяются сроки действия всех сертификатов;
- подпись проверяется в формате **IEEE P1363** (именно его использует ECDSA в JWS, а не DER — частая причина «валидная подпись не проходит»);
- **fail-closed**: без корневого сертификата проверка отключается в любом окружении. Обойти можно только явным `ALLOW_UNVERIFIED_IAP=true`, который запрещён в проде;
- Sandbox-транзакции не дают прав в проде (флаг `ALLOW_SANDBOX_IAP`);
- в результат добавлен `bundleId` — из-за его отсутствия проверка bundleId в `billing.ts` была **мёртвым кодом**.

**Защита от регресса:** `JoseConfig.selfTest()` вызывается на старте в `app.ts` — заведомо поддельный JWS обязан быть отвергнут. В проде провал самопроверки роняет запуск.

**Что нужно от вас:** задать `APPLE_ROOT_CA_PEM` (или `APPLE_ROOT_CERT_PATH`) в переменных Railway. **Без него покупки перестанут подтверждаться** — это осознанный выбор в пользу fail-closed.

Дублирующий `src/routes/subscription.ts` помечен как неподключаемый: он написан под другую схему Prisma и уронит сервер при регистрации.

## P0-2 — Access-токен не истекал никогда

**Где:** `src/utils/tokens.ts`.

**Суть.** `sign(payload, { expiresIn: config.ACCESS_TOKEN_TTL as any })` передавал строку `'1h'`, а `fast-jwt` под `@fastify/jwt` ожидает **число миллисекунд**. Получалось `exp = iat + Math.floor('1h'/1000)` → `NaN`, и claim фактически не выставлялся. Приведение `as any` скрывало несоответствие типов.

Утёкший токен оставался валидным вечно.

**Исправлено:** `exp` считается явно в секундах Unix (стандарт JWT) и не зависит от того, в каких единицах библиотека ждёт TTL. Функция `parseTtlToMs` уже была в файле — её просто не использовали для подписи.

**Дополнительно:** добавлено обнаружение повторного использования refresh-токена. Предъявление уже отозванного токена — признак кражи; теперь это отзывает **все** сессии пользователя, а не просто отдаёт 401 жертве, пока цепочка злоумышленника живёт.

## P0-3 — Бан и разжалование не действовали

**Где:** `src/middleware/auth.ts`.

**Суть.** HTTP-слой безоговорочно доверял claim'ам JWT и **не обращался к БД**. Забаненный продолжал писать и создавать комнаты, разжалованный админ сохранял права, удалённый аккаунт работал по старому токену, а роль бралась из токена. В связке с P0-2 окно «до истечения токена» было бесконечным — бан не срабатывал **вообще никогда**. Websocket-шлюз при этом всё делал правильно; расходился именно HTTP.

**Исправлено:** на каждый запрос сверяемся с БД (роль, `bannedUntil`, `deletedAt`) с кэшем 30 секунд, чтобы не превращать каждый вызов API в запрос к Postgres. Роль берётся **только из БД**. Экспортирован `invalidateUserSnapshot(userId)` для мгновенного применения бана.

При недоступности БД отдаётся `503`, а не `401` — чтобы клиент не разлогинивал пользователя из-за проблем инфраструктуры.

## P1 — исправлено в этом заходе

| Что | Где | Суть |
|---|---|---|
| **`trustProxy`** | `app.ts` | За прокси Railway `request.ip` был IP прокси. Все лимиты по IP складывались в **одно общее ведро** — один злоумышленник исчерпывал лимит для всех, а в аудит-логи писался неверный адрес. |
| **dev-wipe вне прода** | `app.ts` | Маршруты разработки (включая полную очистку БД) регистрировались всегда и защищались только переменной окружения. Теперь в проде их не существует вовсе. |
| **Криптостойкие коды комнат** | `rooms.ts` | Код генерировался через `Math.random()`. Для комнат «по ссылке» этот код — единственный секрет. Теперь `crypto.randomBytes`, плюс исключены путающие символы `0/O` и `1/I`. |
| **Лимит на вход по коду** | `rooms.ts` | `/rooms/join` не был ограничен по частоте — код можно было перебирать. Лимит 20/мин **по пользователю**, а не по IP (за одним адресом провайдера сидят тысячи людей). Заодно устранена 500-я ошибка при отсутствии `code`. |
| **Починен санитайзер** | `security.ts` | `sanitizeText` вырезал теги, а **потом декодировал HTML-сущности**, тем самым восстанавливая вырезанную разметку: `&lt;script&gt;` на выходе становился настоящим `<script>`. Теперь сущности не раскодируются, а экранируются. |

## P0-4 — «Две эры» кода: модерация роняла бы сервер

**Где:** `src/routes/moderation.ts`, `src/routes/web.ts`, `prisma/schema.prisma`.

### moderation.ts — был подключён и полностью нерабочий

Модуль зарегистрирован в `app.ts`, но:

1. **Экспорт был только именованным**, а `app.ts` импортирует его как default. При деплое `fastify.register(undefined)` **роняет сервер на старте**.
2. Создавал **свой `new PrismaClient()`** — второй пул соединений к Postgres.
3. Обращался к несуществующим моделям и полям: `prisma.block` (в схеме `userBlock`), `prisma.message` (`chatMessage`), `blockerId/blockedId` (`blockerID/blockedID`), `userId/friendId` (`userID/friendID`), `user.isModerator` (в схеме `role: UserRole`).
4. **Маршруты не требовали авторизации** — без `preHandler: authenticate` поле `request.user` всегда пустое, поэтому любой запрос получал 401. Модерация не работала вообще.

**Переписан целиком** под реальную схему: общий `prisma`, проверка прав через `UserRole`, авторизация на всех маршрутах, default-экспорт. Дополнительно: автоскрытие считает **разных** заявителей (раньше один человек тремя жалобами скрывал чужое сообщение), блокировка убирает и висящие заявки в друзья (иначе обходилась повторным принятием), бан сбрасывает кэш авторизации и действует мгновенно.

### web.ts — фикс XSS был написан, но не работал

Модуль содержит исправление XSS на публичных лендингах `/r/:code` и `/u/:username` (12 мест экранирования, CSP `default-src 'none'`), но **не был подключён в `app.ts`** — то есть исправление просто не применялось. Там же живёт `/.well-known/apple-app-site-association`, без которого **не работают Universal Links**: ссылка-приглашение открывала сайт вместо приложения.

Подключён без префикса `/api`. Исправлены обращения к несуществующим полям (`room.mediaTitle` принадлежит `WatchHistory`, `user.bio` в схеме нет) и убран второй `PrismaClient`.

### Миграция БД

`prisma/migrations/20260726120000_moderation_gdpr_indexes/migration.sql` — **аддитивная**, данные не удаляются:

- **Модерация:** `Report` получает `targetType`, `targetID`, `comment`, `dueAt`, `resolution` — раньше жалоба могла указывать только на комнату, а App Review требует жалобу на конкретное сообщение и на человека. Флаги `hidden` у `ChatMessage`/`Room` и `shadowbanned` у `User`.
- **GDPR:** проставлены правила `onDelete` для 18 внешних ключей. Раньше у ~13 связей их не было: `prisma.user.delete()` падал по внешнему ключу, а ручное удаление рисковало оставить персональные данные. Каждый сброшенный constraint восстановлен (проверено: 18 DROP = 18 ADD).
- **Производительность:** составные индексы под горячий запрос личных сообщений.

## Как это выкатывать

```bash
# 1. Переменные окружения (обязательно — иначе покупки не подтверждаются)
#    APPLE_ROOT_CA_PEM='-----BEGIN CERTIFICATE-----...'

# 2. Миграция
npx prisma migrate deploy
npx prisma generate     # обязательно: в схеме новые поля

# 3. Сборка и тесты
npm run build && npm test
```

При старте в логах должно появиться `[iap] самопроверка проверки покупок пройдена`. Если вместо этого `САМОПРОВЕРКА ПРОВАЛЕНА` — проверка покупок снова пропускает подделки, разбираться немедленно.

**Порядок важен:** сначала миграция, потом деплой кода. Новый код обращается к полям, которых до миграции нет.
